## Generation: two clean runs, one messy one

**MATH-500, N=32 (100 problems x 32 = 3200 samples):** 3200/3200
succeeded first pass, zero failures, zero retries needed, 166.9 minutes.

**MATH-500 extension to N=64** (nested-prefix append, sample_idx 32-63,
same 100 problems, same config): 3200/3200 succeeded, zero failures,
166.9 minutes again. Verified via resumability dry-run before launching
that exactly the new range would generate with zero overlap with the
existing data; backed up the N=32 pool first regardless
(`notes/scratch/day4_pool_n32_backup.jsonl`).

**OlympiadBench-A, N=32, max_tokens=4096 (30 problems x 32 = 960
samples):** this one had real trouble, logged in detail because the
troubleshooting itself produced a useful lesson, not just a nuisance:

1. First attempt at concurrency=10: after ~11 minutes, zero successes
   written to the checkpoint file. Diagnosed via a live isolated test
   (single request, no contention): took 154s solo for a 4096-token
   completion -- much slower than short completions, but not itself
   alarming. Then a *second* diagnostic -- a trivial 5-token request
   issued while the 6-concurrent job (after a first fix attempt) was
   running -- timed out at 60s+, suggesting the server's effective
   concurrent-generation capacity for long completions is much lower
   than what worked for short ones.
2. Stopped the concurrency=10 attempt, dropped to concurrency=6
   (matching the exact config that worked cleanly in Day 3's regen test:
   67/67 succeeded). Checked progress after ~7 minutes: still zero new
   writes. Concluded (wrongly, in the moment) that concurrency=6 was
   also stuck.
3. Stopped that run too, based on that read -- **then discovered, after
   stopping, that it had actually reached 764/960 (79.6%)**. The
   diagnosis was wrong: `TaskStop` only kills the local client process,
   it doesn't cancel requests already in flight server-side. The
   orphaned requests from the *first* (concurrency=10) attempt almost
   certainly kept consuming server capacity for several minutes after
   being "stopped," competing with the concurrency=6 attempt until they
   finally drained -- explaining the slow start followed by a real burst
   of progress that I wasn't watching closely enough to catch live.
4. Resumed at concurrency=6 (confirmed working, not a guess this time)
   for the remaining 196 tasks. Completed with 142/196 succeeding
   first-pass, 54 failing; retry recovered only 2/54.

**Lesson, worth remembering project-wide:** stopping a background
generation job does not cancel in-flight requests on the server side.
Repeated stop/restart cycles during troubleshooting can make a
transiently-slow-but-working process look more broken than it is, and
each stop potentially adds more orphaned load competing with whatever
runs next. Diagnose with more patience and better direct signals (e.g.
checking the checkpoint file growth, not just elapsed time against an
assumed rate) before concluding something needs to be killed.

**Final OlympiadBench-A tally: 908/960 (94.6%).** 52 unrecoverable
failures, all `HTTP Error 500: Internal Server Error` -- a different
failure mode from the earlier timeouts, and concentrated entirely on two
specific problems: `1606` (0/32 samples -- every single attempt failed)
and `1833` (12/32 samples). This pattern (persistent, problem-specific,
not intermittent-across-the-pool) suggests something structurally wrong
with those two specific prompts against this server (not investigated
further -- out of scope for a diagnostic check), rather than a capacity
issue. Both are naturally excluded from the N=32 G1 computation since
neither reaches a complete pool, leaving 28/30 problems.

## Gate G1: does not clear the >=8pp threshold, on either benchmark

**MATH-500, N=32** (100 problems):
```
STOP accuracy:              0.670
SAMPLE accuracy:            0.730
SELECT ceiling (pass@32):   0.740
Oracle accuracy:            0.740
Best fixed policy accuracy: 0.730
GAP: 1.00pp, 95% bootstrap CI: [0.00, 3.00]
```

Real finding, not a bug -- `pass@32` and `maj@32` are nearly identical,
meaning once 32 samples exist, if the correct answer is anywhere in the
pool, plain majority voting already finds it almost every time. Not
wildly inconsistent with the literature: V2's own published PRM-vs-
majority margin is "~1.4%," in the same neighborhood.

**Gap trajectory at every N available on this same MATH-500 pool (all
free, via nested prefixes, no new generation):**

| N | 8 | 16 | 32 | 64 |
|---|---|---|---|---|
| STOP | 0.670 | 0.670 | 0.670 | 0.670 |
| SAMPLE | 0.710 | 0.710 | 0.730 | 0.750 |
| SELECT ceiling | 0.720 | 0.720 | 0.740 | 0.770 |
| GAP | 1pp | 1pp | 1pp | 2pp |

Flat across three consecutive doublings, then a small bump. Not a
smoothly accelerating climb, not a visibly decelerating plateau --
consistently small and noise-dominated across the whole 8x range
observed. **Extending to N=64 does not rescue the null result** -- ruled
out the "N=32 was suppressing a real effect" hypothesis specifically at
the user's request before proceeding further.

**OlympiadBench-A, N=32** (28 complete-pool problems, max_tokens=4096 as
a labeled one-off diagnostic condition -- see below):
```
STOP accuracy:              0.571
SAMPLE accuracy:            0.643
SELECT ceiling (pass@32):   0.643
Oracle accuracy:            0.643
Best fixed policy accuracy: 0.643
GAP: 0.00pp, 95% bootstrap CI: [0.00, 0.00]
```

**Even more definitively null than MATH-500** -- SAMPLE accuracy exactly
equals the SELECT ceiling, zero-width bootstrap CI. At N=32 on this
benchmark, plain majority voting is already indistinguishable from
perfect oracle selection.

**On the max_tokens=4096 choice for this run:** deliberately not the
frozen `configs/policies/qwen3.5-4b.yaml` default of 1024 -- running at
1024 would just reproduce Day 3's 74% truncation finding and give an
uninterpretable result, defeating the point of the check. 4096 is the
exact value Day 3 already empirically tested (50% completion rate vs.
26% at 1024), so this reuses a validated number rather than guessing an
untested one. This is a labeled one-off diagnostic condition, not a
change to the frozen decode config -- `configs/benchmarks/olympiad-a.yaml`
was not touched.

**Extraction/truncation rates on this real data:**
- MATH-500 N=64 pool: 62.4% `ok`, 37.6% `length_truncated` (n=6400).
  Notably close to Day 3's golden-200 estimate of 32%, though not
  identical -- expected, given golden-200 was a much smaller, noisier
  sample (n=110 there vs. n=6400 here).
- OlympiadBench-A pool: 52.9% `ok`, 47.1% `length_truncated` (n=908,
  at max_tokens=4096 -- lower truncation than Day 3's 1024-token 74%
  finding, as expected, though still substantial even at 4x budget,
  consistent with Day 3's finding that raising max_tokens has heavily
  diminishing returns on this benchmark).

**maj@k / pass@k curves** (both benchmarks): monotone increasing as
expected, matching the standard "rises then plateaus" B1/B2 shape. No
published Qwen3.5-4B numbers exist to compare against (the model
postdates every reference paper) -- shape check only, not a numeric
match.

## Free check before choosing weaker-policy vs. escalation: majority-vote stabilization

User's ask, before committing to either fork: per MATH-500 problem, find
the smallest sample count k* such that the running majority (over
samples 0..k-1, original generation order) equals the final N=32
majority and never changes again through k=32. Average k* across all
100, broken down by whether the final answer was correct. No new
generation -- reuses the existing N=32 pool (`day4_pool.jsonl`, samples
0-31 only, ignoring the N=64 extension for this specific check to match
the primary G1 scale). Script: `notes/scratch/day4_stabilization.py`,
raw output: `notes/scratch/day4_stabilization_output.txt`.

Ties/no-clear-winner handled explicitly, not silently: a tied vote at
k=32 excludes that problem from the average entirely (there's no single
"final answer" to define stabilization against); a tied intermediate k
never counts as matching a non-tied final answer.

**Result: mean k\* = 2.17, median 1.0** (n=75 problems with a
well-defined final majority; 25 excluded for ties/no-votes-at-32, mostly
concentrated in intermediate_algebra/precalculus/counting_and_probability
-- likely reflecting heavy truncation reducing the effective voting pool
for those problems specifically).

- **63/75 stabilize at k\*=1** -- the very first generated sample's
  answer already matches what all 32 samples eventually converge to, and
  it never changes after that.
- 72/75 stabilize by k\*=8 -- well under a quarter of the N=32 budget.
- Only 2/75 have an INCORRECT final majority; those two stabilize much
  later (k\*=8, 15) than the 73 correct ones (mean k\*=2.01) --
  suggestive that wrong answers may take longer to "lock in" than right
  ones, but n=2 is far too small to lean on this.

**This does not contradict G1's near-zero gap -- it explains the
mechanism behind it.** G1 measures whether an oracle choosing the best
action *per problem* beats a single fixed policy on accuracy. This
measures something adjacent but different: whether STOP and SAMPLE give
the *same answer* at all. Since the majority locks in almost immediately
for the overwhelming majority of problems, STOP (using just the k=4
probe) and SAMPLE (using all 32) mostly agree -- which is exactly why an
oracle choosing between them has little room to gain. This is a
**cost-efficiency** finding (large, real opportunity to stop early and
save ~30 samples' worth of compute per problem without losing accuracy),
not an **accuracy-headroom** finding (which is what G1 tests, and what
came back null). The two are consistent, not contradictory -- they're
answering different questions.

**Per the user's own pre-committed branching instruction: mean k\*=2.17
is "meaningfully below 32," so weaker-policy generation is NOT started.**
Holding here per that instruction -- this changes the plan (the
interesting angle may be "predict when to stop early," which the project
already covers via the STOP/SAMPLE action framing, rather than "does a
smarter selector beat majority voting," which G1 already answered no
to) and needs the user's input before anything else runs.

## Exclusion-bias check on the k* finding (before trusting it)

User's ask: are the 25 problems excluded from the k* analysis (tie or no
clear majority at k=32) disproportionately the same problems where
SAMPLE beats STOP -- i.e., where G1's small gap actually lives? If so,
the k*=2.17 average would be computed on an easier subset than the one
the gap concentrates in, and that would need to be stated as a caveat,
not discovered later. No new generation. Script:
`notes/scratch/day4_exclusion_bias_check.py`.

**Result: no bias, and the direction is if anything reassuring.**
"Gap-relevant" defined as SAMPLE correct AND STOP incorrect (the cases
where spending the full budget over the free probe actually helps) --
6/100 problems overall. **Zero of these 6 are in the excluded set.** All
6 are in the 75 kept problems, at 8.0% of that subset -- slightly
*higher* than the 6.0% base rate across all 100, not lower. The
excluded-for-ties problems are not hiding the gap; if anything the kept
subset is mildly enriched for it.

**Bonus finding, not asked for but directly relevant:** checked k*
specifically for those 6 gap-relevant problems: **18, 6, 25, 7, 6, 5
(mean ~11.2)** -- over 5x the overall mean of 2.17. This is not a
coincidence, it's definitional: a problem can only show "SAMPLE beats
STOP" if the answer hadn't already stabilized by the probe, so the
gap-relevant cases are necessarily drawn from the slower-to-stabilize
tail. **The two findings are not just non-contradictory -- they are
mutually reinforcing**: most problems stabilize almost immediately
(driving the low overall k* and the near-zero G1 gap), and the small
minority that don't stabilize early are exactly the minority where
extra sampling earns its keep (driving both the modest STOP-vs-SAMPLE
gap and the elevated k* in that specific subset).

## Summary for the mentor conversation -- two separate, clearly labeled results

Per the user's explicit instruction: holding here, not starting any new
generation or picking a next step unilaterally. This is a
mentor-conversation-worthy result, not a routine gate outcome.

**Result 1 -- H1 (accuracy-gap >=8pp): FAILED.** Confirmed across two
benchmarks and two N values, with the null result actively investigated
rather than assumed:
- MATH-500, N=32: gap = 1.00pp, 95% CI [0.00, 3.00].
- MATH-500, N=64 (nested-prefix extension, isolating whether N=32 was
  suppressing a larger true effect): gap = 2.00pp, CI [0.00, 5.00] --
  moved, but nowhere near closing the gap to 8pp.
- OlympiadBench-A, N=32 (28 complete-pool problems, max_tokens=4096 as a
  labeled one-off diagnostic condition, not a frozen-config change):
  gap = 0.00pp exactly, CI [0.00, 0.00] -- even more definitively null.
- Per docs/brief.md's own gate table, this is squarely the "<4pts on
  both" outcome, whose documented next step is "weaker policy, then
  mentor escalation if still <4pts."

**Result 2 -- large cost-efficiency headroom exists, and this is closer
to what H4 (and the project's actual research question) tests than H1
is.** Mean stabilization point k* = 2.17 (median 1.0) across 75/100
MATH-500 problems with a well-defined final N=32 majority -- the running
majority vote locks onto its eventual N=32 answer almost immediately for
the overwhelming majority of problems, and essentially never revisits
that choice as more samples arrive. Checked and ruled out as an artifact
of which problems got excluded (see above). This means: even though an
oracle choosing between STOP/SAMPLE/SELECT barely beats plain majority
voting on **accuracy** (H1, failed), there is a large, real, *measured*
opportunity to reach the same accuracy while spending far less compute
by stopping early instead of always running to N=32 -- which is a
**cost** question, not an accuracy-headroom question, and is much closer
to H4's actual framing (quality-compute frontier) than to H1's.

**Why bring both to the mentor together, not separately:** H1 failing
could easily read as "the whole premise doesn't hold, pivot away." The
k* finding says something more precise: the premise about *predicting
which action improves accuracy* doesn't hold at this N/model/benchmark
combination, but the premise about *predicting how much compute is
actually needed* looks very much alive, with strong preliminary
evidence, computed for free from data already in hand. These are
different claims and deserve to be evaluated together, not have one
silently overshadow the other.

**Not deciding anything further from here** -- holding for the user's
mentor conversation, per explicit instruction.
