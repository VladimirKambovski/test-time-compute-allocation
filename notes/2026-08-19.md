## Decisions made
- **OlympiadBench config: `OE_TO_maths_en_COMP`** (674 rows). Not specified
  anywhere in brief.md — OlympiadBench has 8 configs split by open-ended
  vs. theorem-proof, multimodal vs. text-only, math vs. physics, English
  vs. Chinese, competition vs. exam. Chose Open-Ended (checkable final
  answer — theorem-proof isn't), Text-Only (matches the text-only
  PRM/pipeline), maths (matches Math-PRM and MATH-500's domain), English
  (matches MATH-500), Competition-level (matches "Olympiad" framing).
  Presented as a recommendation with rationale; user confirmed.
- **AIME25 source: `opencompass/AIME2025`** over `math-ai/aime25`. Both are
  correct (15+15=30). brief.md's own config stub already flagged this as
  unresolved ("no single canonical HF copy exists yet"). User picked
  opencompass over my recommendation (I'd suggested it too, for its
  standard-eval-framework provenance) — same choice, confirmed by user.
- **Seed and procedure for the dev/held-out split**, at user's explicit
  request (they asked me to confirm a seeded shuffle was used, not row
  order, before freezing): sorted all 674 `OE_TO_maths_en_COMP` IDs
  ascending, shuffled with Python stdlib `random.Random(20260818).shuffle()`
  (deterministic Mersenne Twister for a fixed seed), took [0:300] as slice
  A (dev), [300:400] as slice B (held-out) — disjoint by construction.
  Remaining 274 IDs unused/reserved, no current use assigned.
- **AIME25 problem IDs minted as `{config}-{zero_padded_row_index}`** (e.g.
  `AIME2025-I-00`) since the dataset has no native per-row ID field — only
  `question`/`answer` columns.
- **Hash method**: SHA-256 of `json.dumps(sorted(problem_ids),
  separators=(',', ':'))`, UTF-8 encoded. Documented in both heldout-*.yaml
  files so it's independently reproducible.
- **Did not commit raw held-out question/answer text to the repo** — only
  ID lists and hashes. Rationale: invariant #8's discipline is easier to
  keep if the actual problem content isn't sitting in a routinely-browsed
  file; Day 18 generation re-fetches content fresh from the pinned
  `dataset_id`+`dataset_revision`, which is the more reproducible pattern
  anyway (content is content-addressed by the dataset commit, not
  duplicated locally where it could drift). Not specified anywhere,
  flagging the reasoning here rather than silently doing it.
- **Extended "pin model revisions" to also pin dataset revisions**
  (`dataset_revision` field, HF dataset commit SHA) for
  `Hothan/OlympiadBench` and `opencompass/AIME2025`, alongside the model
  revision pins for `Qwen/Qwen3.5-4B` and `Qwen/Qwen2.5-Math-PRM-7B`. Same
  rationale as model pinning (invariant #3 — pool identity), same API
  mechanism (HF's `/api/models` and `/api/datasets` both expose `sha`).
  Not explicitly asked for by the roadmap's exact wording ("model
  revisions") but a direct, low-risk extension of the same principle — did
  not block on asking, flagging here instead.
- **Pinned `vllm>=0.17.0`** in `pyproject.toml` (was unpinned, which
  resolved to `vllm==0.1.3` and tried to source-build against a
  nonexistent local CUDA toolchain). 0.17.0 is the first vLLM release with
  full Qwen3.5 architecture support.
- **Pinned Python to 3.10** via a new `.python-version` file. `vllm`'s
  transitive dependency `xgrammar==0.2.5` only ships a `cp310` wheel;
  3.11 and 3.12 both failed to resolve. Verified a clean `uv sync` (no
  flags) now picks 3.10 automatically and completes successfully.
- MATH-500 (`configs/benchmarks/math500.yaml`) and the Bedrock frontier
  anchor's `model_id: null` were NOT touched today — out of Day 2's scope
  (MATH-500 revision pin isn't needed until Day 4; Bedrock model choice
  isn't needed until Day 15/18, and picking a specific one is a real
