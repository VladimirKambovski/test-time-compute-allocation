  stale** — it's been a plain PyPI package since early versions. Installed
  `math-verify[antlr4_13_2]>=0.9.0` normally, per the project's own README
  recommendation to pin the antlr4 runtime extra.
- **Found and specifically guarded against a real math_verify gotcha**,
  verified empirically against the installed 0.9.0 source (not assumed
  from docs): given two *disagreeing* `\boxed{}` values in one completion
  (e.g. a model that second-guesses itself), `math_verify.parse()` doesn't
  flag ambiguity — it silently returns a SymPy **set** of both values
  (`{41, 43}`). Fed into `verify()` against a single gold number, that's
  indistinguishable from a genuine wrong answer: exactly the
  silent-incorrect-instead-of-taxonomy-status failure CLAUDE.md invariant
  #6/#7 is meant to prevent. Built `extraction.py`'s own brace-balanced
  `find_boxed_spans()` specifically to catch this: every boxed span is
  parsed and cross-checked individually, and disagreement is surfaced as
  `extraction_ambiguous`, never passed through to `verify()` as a set.
- **Also verified (not assumed) that `math_verify.verify(...,
  raise_on_error=False)` — the default — silently returns `False` on an
  internal timeout/error**, which is the same silent-incorrect problem one
  level down (at the equivalence-check stage rather than extraction).
  `equivalence.py` always calls `verify(..., raise_on_error=True)` and
  converts the resulting `TimeoutException` into an explicit
  `equivalence_timeout` status.
- **"Canonicalization" is not a separate module** — `math_verify.parse()`
  already returns a canonical SymPy representation, so `answers/`'s job is
  orchestration (extraction disambiguation + equivalence-status mapping)
  around that, not a third canonicalization layer. Documented this
  reasoning in `answers/__init__.py` rather than silently deviating from
  brief.md's three-part "extraction, canonicalization, equivalence"
  phrasing without explanation.
- **A `\boxed{}` that exists syntactically but contains nothing that
  parses to a usable value** (empty, or non-math content) is mapped to
  `no_boxed_answer`, not `extraction_ambiguous` — ambiguity implies
  multiple *disagreeing candidates*, and there are none in that case. A
  judgment call within the closed taxonomy's latitude; flagging the
  reasoning rather than treating it as obvious.
- Changed `tests/test_answer_equivalence.py`'s two stub tests from bare
  `raise NotImplementedError` to `pytest.mark.skipif` with an explicit,
  dated reason pointing at this blocker, so a test run today reads as
  "known-blocked" rather than "broken." `tests/test_taxonomy.py` was

### Four real bugs found and fixed during the hand-check

The hand-check did its job -- an implausible aggregate result (196/196
"not equivalent" on the first pass) triggered investigation, which
surfaced four separate, real correctness bugs in `src/marginal_token/
answers/`, each fixed with a regression test before the fixture was
finalized:

1. **`check_equivalent` fed `verify()` a raw, unparsed gold string.**
   `math_verify.verify()` does not reliably canonicalize a bare string
   despite its type signature accepting one -- `verify("4", parse("\boxed
   {4}")[0])` empirically returns False. This alone caused the initial
   196/196 false-negative result. Fixed: gold is now always routed
   through `math_verify.parse()` internally.
2. **Truncation check ran after, not before, the plain-text fallback.**
   A completion cut off by `max_tokens` with no `\boxed{}` used to fall
   through to a full-text `parse()` fallback first, which could pick up a
   spurious intermediate equation from mid-derivation scratch work and
   credit it as the final answer -- regardless of truncation. Confirmed
   on two real completions (both `finish_reason: "length"`, zero `\boxed{
   }` anywhere, yet a stray equation like "$c=1$" got extracted and
   verified True against an unrelated gold). Fixed: `finish_reason ==
   "length"` with no boxed span now wins outright, no fallback attempted.
3. **Bare boxed-span content parsed incorrectly, not just incompletely.**
   `math_verify.parse()` on stripped span content (no `\boxed{}` wrapper,
   no `$` anchor) silently mis-parses LaTeX commands to a WRONG value
   instead of failing: `parse("3\sqrt{5}")` → bare `Integer(3)` (drops
   `\sqrt{5}` entirely); `parse("\{1,2,3\}")` → `3` (collapses a 3-element
   set to its last element); `parse("(0,5)")` → `5`; `parse("2\pi")` → `2`;
   `parse("1+274i")` → `1`. Caught via a real completion where gold
   `3\sqrt{5}` was compared against a silently-truncated extracted value
   of bare `3`. Fixed: span content is now re-wrapped as `\boxed{...}`
   before re-parsing, routing through math_verify's dedicated
   boxed-content handling rather than a bare parse.
4. **Same bug, unpatched copy, in gold-string parsing.** `_ensure_parsed`
   in `equivalence.py` had the identical bare-parse problem for gold
   strings: `parse("p - q")` → `[]` (fails safely); `parse("\left(3, \frac
   {\pi}{2}\right)")` → bare `3` (silently drops the tuple). The second
   produced a real false-negative: a genuinely correct `(3, pi/2)`
   prediction was scored "not equivalent" because gold silently collapsed
   to `3`. Fixed: gold strings are now `$`-wrapped before parsing
   (verified safe even when the source string is already `$`-wrapped).

All four are logged in the affected modules' docstrings and covered by
new regression tests in `tests/test_answers_smoke.py` (24 tests total now,
up from 19).

## Follow-up: OlympiadBench-A max_tokens investigation (requested before G2's final call)

User asked for real percentiles before recommending a max_tokens bump for
OlympiadBench-A specifically (MATH-500 explicitly out of scope for this
change -- its 32% truncation is flagged, not fixed, per instruction).

**The premise needed correcting first.** A sample truncated at 1024 only
tells us "needs more than 1024" -- not its true length (right-censored
data). Re-generating the same 67 truncated problems at a much higher cap
was necessary before any percentile is meaningful. Re-ran them at
`max_tokens=4096` (4x): 67/67 requests succeeded, but **45/67 (67%) were
STILL truncated at 4096.** Checked the still-truncated completions for
degenerate repetition/looping (a common small-model failure mode) via a
verbatim-substring check: 0/45 showed it -- these read as genuine,
if very long and case-by-case, exhaustive derivations on hard
combinatorics/number-theory problems, not obviously stuck loops (though a
crude substring check can't rule out subtler non-convergence).

**Combined picture across all 90 OlympiadBench-A samples:**

| max_tokens | resolved (reached `stop`) | rate |
|---|---|---|
| 1024 (current) | 23/90 | 26% |
| 4096 (4x) | 45/90 | 50% |

Percentiles among the 45 *resolved* samples (both rounds combined) --
**this underestimates the true population percentile**, since the other
45/90 are still censored at >4096: p50=863, p75=1722, p90=2302, p95=2615,
max observed=3962.

**Honest conclusion: there is no max_tokens value the current data
supports recommending for a 90-95% completion target.** Quadrupling the
budget only moved completion from 26% to 50% -- a heavily diminishing
curve, not a case where "a bit more room" closes the gap. Extrapolating
further (8192? 16384?) isn't supported by evidence in hand and every
doubling so far has shown worse-than-linear returns. Framed differently,
this may not be a "config problem" at all: on Olympiad-level problems, a
4B non-thinking model frequently doesn't converge to a boxed answer
within any practical budget -- which is arguably itself informative for
the project's own premise (the H1 distinction between "hard-but-solvable"
and "hard-and-unsolvable" queries; a chronically-non-converging problem
under SAMPLE is exactly the kind of case ABSTAIN exists for). **Not
recommending a specific number. Not changing `configs/benchmarks/
olympiad-a.yaml` or any policy config.** Presenting the real data for the
user's call instead of forcing a clean answer the evidence doesn't
support.
