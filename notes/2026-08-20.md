  raise_on_error=False)` — the default — silently returns `False` on an
  internal timeout/error**, which is the same silent-incorrect problem one
  level down (at the equivalence-check stage rather than extraction).
  `equivalence.py` always calls `verify(..., raise_on_error=True)` and
  converts the resulting `TimeoutException` into an explicit
  `equivalence_timeout` status.

  already returns a canonical SymPy representation, so `answers/`'s job is
  orchestration (extraction disambiguation + equivalence-status mapping)

  reasoning in `answers/__init__.py` rather than silently deviating from
  brief.md's three-part "extraction, canonicalization, equivalence"
  phrasing without explanation.
- **A `\boxed{}` that exists syntactically but contains nothing that
  parses to a usable value** (empty, or non-math content) is mapped to
  `no_boxed_answer`, not `extraction_ambiguous` — ambiguity implies
  multiple *disagreeing candidates*, and there are none in that case. A

### Four real bugs found and fixed during the hand-check

The hand-check did its job -- an implausible aggregate result (196/196
"not equivalent" on the first pass) triggered investigation, which
surfaced four separate, real correctness bugs in `src/marginal_token/
answers/`, each fixed with a regression test before the fixture was
finalized:

1. **`check_equivalent` fed `verify()` a raw, unparsed gold string.**
   `math_verify.verify()` does not reliably canonicalize a bare string
   despite its type signature accepting one -- `verify("4", parse("\boxed
   {4}")[0])` empirically returns False. This alone caused the initial
   196/196 false-negative result. Fixed: gold is now always routed
   through `math_verify.parse()` internally.
2. **Truncation check ran after, not before, the plain-text fallback.**
   A completion cut off by `max_tokens` with no `\boxed{}` used to fall
   through to a full-text `parse()` fallback first, which could pick up a
   spurious intermediate equation from mid-derivation scratch work and
   credit it as the final answer -- regardless of truncation. Confirmed
   on two real completions (both `finish_reason: "length"`, zero `\boxed{
   }` anywhere, yet a stray equation like "$c=1$" got extracted and
   verified True against an unrelated gold). Fixed: `finish_reason ==
   "length"` with no boxed span now wins outright, no fallback attempted.
3. **Bare boxed-span content parsed incorrectly, not just incompletely.**
   `math_verify.parse()` on stripped span content (no `\boxed{}` wrapper,
   no `$` anchor) silently mis-parses LaTeX commands to a WRONG value
   instead of failing: `parse("3\sqrt{5}")` → bare `Integer(3)` (drops
   `\sqrt{5}` entirely); `parse("\{1,2,3\}")` → `3` (collapses a 3-element
   set to its last element); `parse("(0,5)")` → `5`; `parse("2\pi")` → `2`;
   `parse("1+274i")` → `1`. Caught via a real completion where gold
   `3\sqrt{5}` was compared against a silently-truncated extracted value
   of bare `3`. Fixed: span content is now re-wrapped as `\boxed{...}`
   before re-parsing, routing through math_verify's dedicated
   boxed-content handling rather than a bare parse.
4. **Same bug, unpatched copy, in gold-string parsing.** `_ensure_parsed`
   in `equivalence.py` had the identical bare-parse problem for gold
   strings: `parse("p - q")` → `[]` (fails safely); `parse("\left(3, \frac
   {\pi}{2}\right)")` → bare `3` (silently drops the tuple). The second
   produced a real false-negative: a genuinely correct `(3, pi/2)`
   prediction was scored "not equivalent" because gold silently collapsed
   to `3`. Fixed: gold strings are now `$`-wrapped before parsing
   (verified safe even when the source string is already `$`-wrapped).

All four are logged in the affected modules' docstrings and covered by
new regression tests in `tests/test_answers_smoke.py` (24 tests total now,
up from 19).

## Post-Day-3 finding: OlympiadBench-A benchmark choice settled; `length_truncated` must be a first-class stratifying variable, not collapsed into "incorrect"

### The benchmark question is closed

Two cheap checks, run to decide between filtering OlympiadBench-A
further or switching to AMC23, both point the same direction and rule
out "wrong benchmark" as the explanation for the 74% truncation rate
found in the golden-200 hand-check:

1. **OlympiadBench-A, reference-solution-length correlation** (free --
   reused existing Day-3 generation data, no new inference). Fetched the
   dataset's own reference `solution` field for the 30 tested problems.
   Point-biserial correlation between solution length and truncation:
   **r = 0.428.** Truncated problems have reference solutions **~3.8x
   longer on average** (1987 vs 526 chars), ~2.8x longer at the median.
   The model is truncating on problems that are *objectively* longer to
   explain, even by the human reference -- consistent with genuine
   difficulty, not a serving artifact.
2. **AMC23, direct completion-rate check** (`math-ai/amc23`, 40 problems,
   all run at `max_tokens=1024`, single sample each). **Completion rate:
   11/40 = 28%** -- essentially identical to (marginally worse than)
   OlympiadBench-A's 26%, despite AMC being a *lower* competition tier
   than Olympiad-level problems. Checked both truncated sets for
   degenerate verbatim repetition/looping: 0/29 (AMC23) and 0/45
   (OlympiadBench-A regen) -- these are genuine long derivations, not a
   stuck model.

**Conclusion, decided 2026-08-20: staying with OlympiadBench-A.** This is
a property of this model (4B, non-thinking mode) doing verbose
case-by-case derivations on competition-style math generally -- not
something specific to Olympiad-level difficulty, and not something a
different benchmark choice would route around. AMC23 would also only
offer 40 total problems vs. OlympiadBench-A's 300.

### The real, durable finding: truncation is signal, not noise

This is the part worth carrying into the report, not just the resolved
benchmark question. **A `length_truncated` sample and an
`ok`-but-wrong sample represent two qualitatively different situations,
and treating them as the same "incorrect" outcome throws away exactly
the information this project is trying to predict:**

- **`length_truncated`** = the policy never got far enough to state an
  answer at all, within the budget bought. This is *coverage-limited by
  budget* -- more of the same action (SAMPLE: more samples at the same
  token cap) won't fix it if the underlying issue is that any single
  attempt needs more tokens than the cap allows. The informative
  signal here points toward SEARCH (bounded, guided reasoning might
  reach a conclusion within budget where free-form generation
  meanders) or ABSTAIN (if even generous budgets don't converge,
  declining is the honest action) -- not toward "sample more" or
  "select from what you have," since there may be nothing usable to
  select from.
- **`ok` but wrong** = the policy completed normally, stated a
  confident final answer, and got it wrong. This is a *reasoning
  failure*, not a budget failure. The informative signal here points
  toward SELECT (PRM-weighted picking among several confident-but-wrong
  candidates might still recover the right one) or SAMPLE (more
  independent attempts might land on the correct answer by chance),
  since the model demonstrably *can* reach a stated conclusion here --
  it's just often the wrong one.

Collapsing both into a single "not correct" bucket for oracle-action
labeling or for E2's difficulty bands would erase precisely the
distinction that should drive which action the controller learns to
prefer. A query where the probe's 4 samples are mostly `length_truncated`
and a query where the probe's 4 samples are mostly `ok`-but-disagreeing
are different problems calling for different purchases, even if both
currently "fail" under a naive binary correct/incorrect view.

**Concretely, this needs to be carried forward into:**

- **Day 6 (`pools`/`generation`)** -- no new work needed here as such;
  the failure taxonomy already treats `length_truncated` as a first-class
  status (invariant #7) and Day 3's `answers/` module already tags it
  correctly (verified against 200 real completions). The requirement is
  that nothing downstream *discards* this distinction when it aggregates.
- **Day 8 (`selectors`/`evaluation`)** -- when computing per-action
  accuracy/oracle labels, the fraction of a pool's samples that are
  `length_truncated` vs. `ok`-but-wrong should be tracked and reported
  alongside plain correctness, not folded into one failure rate.
- **Day 12 (E2, the action-value landscape)** -- the five difficulty
  bands are defined by pass@1 (per docs/brief.md §19), but truncation
  rate at a given budget is a second, partially-independent axis worth
  cross-tabulating: a "hard" band by pass@1 could be hard because the
  model gets there and is wrong, or hard because it rarely gets there at
  all within budget -- these likely call for different oracle actions
  even within the same difficulty band.
- **Day 13 (trace inspection, V4/length-bias analysis)** -- when
  inspecting the "30 traces where PRM-argmax picked wrong and majority
  was right" (roadmap Day 13), whether the losing/winning samples were
  `length_truncated` is directly relevant context, not incidental.
- **Predictor features (§16)** -- brief.md already lists "truncation
  fraction" under the Hygiene feature group, which is the right
  mechanism for the PREDICT stage. This finding is about making sure the
  same distinction is *also* honored in DIAGNOSE's landscape mapping and
  action-labeling, not only in the eventual feature table.

Not proposing a brief.md change today -- the oracle action definition in
§4 ("the cheapest action yielding a correct answer, or A4 if none does")
doesn't need to change; what needs to change is that whichever module
computes *why* an action didn't yield a correct answer keeps
`length_truncated` visible as its own category through to reporting,
rather than treating "didn't yield a correct answer" as a single
opaque bucket. Flagging as a design requirement for Days 6-13, not
implementing anything today since none of those modules exist yet.

## Pre-Day-4 check: does N=32 threaten H1/G1's statistical reliability?

Requested before real generation starts, given G1 is "the gate the whole
project's premise depends on." golden-200 can't answer this directly --
it has only 3 samples/problem, nowhere near N=32/64 scale, so there's no
way to empirically measure sampling variance at those N from it. Built a
Monte Carlo simulation of the actual G1 mechanics instead:
`notes/scratch/n32_vs_n64_g1_power.py`.

**A real methodological bug surfaced and got fixed along the way, not
just a coding mistake:** the first version included the pass@N-based
SELECT oracle ceiling as a candidate for "best fixed policy," alongside
STOP and SAMPLE. Since pass@N (correct answer exists anywhere in the
pool) mathematically dominates STOP/SAMPLE on every problem -- majority-
of-a-subset can never succeed if the correct answer isn't in the pool at
all -- this made "always apply the SELECT ceiling" simultaneously the
oracle AND the best fixed policy, collapsing the gap to exactly 0.00pp
by construction, for every N, every distribution, every trial. This
isn't a modeling nuance -- it's the same distinction brief.md already
draws with its own "selection gap (pass@k - best selector)" metric, and
initially collapsing it revealed a real ambiguity worth resolving
explicitly: **on Day 4, without a working PRM, "best fixed policy" can
only be computed from policies actually runnable today (STOP, SAMPLE).
The pass@N ceiling belongs only on the oracle side**, representing the
headroom a real PRM might eventually capture. Fixed and reran.

**Method (after the fix):** per-problem correctness modeled as
Bernoulli(p_i), p_i ~ Beta(a,b) swept across three distinct assumptions
(U-shaped, uniform, skewed-harder) to check the conclusion isn't an
artifact of one arbitrary distribution -- there's no real N=32/64-scale
data yet to calibrate against, so this is honestly a simulation, not a
fit. Wrong answers spread across 4 fixed buckets (standard simplifying
assumption for majority-vote analysis). 3000 Monte Carlo trials per
(N, distribution) for the gap-distribution check; a second simulation
(300 reps x 2000 bootstrap resamples) reproduces G1's actual accept test
end to end -- draw one pool, compute the paired bootstrap CI on the
oracle-vs-best-fixed gap, check if it excludes 0 -- exactly what G1 will
really do on Day 4.

**Results:**

| Distribution | N=32 gap | N=64 gap | P(bootstrap CI excludes 0), both N |
|---|---|---|---|
| U-shaped | 25.3 +/- 4.4pp | 26.3 +/- 4.4pp | 1.00 |
| Uniform | 25.3 +/- 4.4pp | 24.0 +/- 4.3pp | 1.00 |
| Skewed harder | 41.9 +/- 4.8pp | 41.1 +/- 5.0pp | 1.00 |

Across all three distributions and 3000 trials each, the **standard
deviation of the gap is essentially identical between N=32 and N=64**
(differences of ~0.05-0.15pp -- noise-level, not a real effect). The
simulated bootstrap test excludes zero 100% of the time at both N values,
for all three distributions.

**Why:** the dominant source of variance in this statistic is
*between-problem* heterogeneity (which 100 problems happen to land in
the pool), not *within-problem* sampling noise from a finite N.
Averaging over 100 problems already washes out most of the per-problem
N-level noise -- halving N from 64 to 32 only shrinks an already-minor
variance component.

**Conclusion: stable. Not flagging back per the "if stable, note and move
on" instruction.** Caveat, not a blocker: this is a simulation with
stated assumptions (Bernoulli per-sample correctness, 4 wrong-answer
buckets), not fit to real data -- there's no real N=32/64-scale pool yet
to check them against. Worth a quick real sanity check once Day 4's
actual pool exists, comparing observed maj@N/pass@N variance to what
this model predicted.
