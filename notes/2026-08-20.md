## Decisions made
- **Scope split for today, confirmed with user first:** SSH/GPU access
  isn't set up yet (user: "ill have it tommorow"), and this sandbox has no
  GPU/CUDA and no working API credentials (checked: no `nvidia-smi`, no
  `torch.cuda`, no HF/OpenAI/Anthropic API keys in env). Rather than guess
  at a workaround (e.g. fabricating synthetic "model predictions" and
  passing them off as a hand-checked golden set), presented the blocker
  and two options; user chose to build `answers/` now and defer the
  generation-dependent pieces rather than stop entirely.
- **`math-verify`'s "install per its own repo instructions" comment was
  stale** — it's been a plain PyPI package since early versions. Installed
  `math-verify[antlr4_13_2]>=0.9.0` normally, per the project's own README
  recommendation to pin the antlr4 runtime extra.
- **Found and specifically guarded against a real math_verify gotcha**,
  verified empirically against the installed 0.9.0 source (not assumed
  from docs): given two *disagreeing* `\boxed{}` values in one completion
  (e.g. a model that second-guesses itself), `math_verify.parse()` doesn't
  flag ambiguity — it silently returns a SymPy **set** of both values
  (`{41, 43}`). Fed into `verify()` against a single gold number, that's
  indistinguishable from a genuine wrong answer: exactly the
  silent-incorrect-instead-of-taxonomy-status failure CLAUDE.md invariant
  #6/#7 is meant to prevent. Built `extraction.py`'s own brace-balanced
  `find_boxed_spans()` specifically to catch this: every boxed span is
  parsed and cross-checked individually, and disagreement is surfaced as
  `extraction_ambiguous`, never passed through to `verify()` as a set.
- **Also verified (not assumed) that `math_verify.verify(...,
  raise_on_error=False)` — the default — silently returns `False` on an
  internal timeout/error**, which is the same silent-incorrect problem one
  level down (at the equivalence-check stage rather than extraction).
  `equivalence.py` always calls `verify(..., raise_on_error=True)` and
  converts the resulting `TimeoutException` into an explicit
  `equivalence_timeout` status.
- **"Canonicalization" is not a separate module** — `math_verify.parse()`
  already returns a canonical SymPy representation, so `answers/`'s job is
  orchestration (extraction disambiguation + equivalence-status mapping)
  around that, not a third canonicalization layer. Documented this
  reasoning in `answers/__init__.py` rather than silently deviating from
  brief.md's three-part "extraction, canonicalization, equivalence"
  phrasing without explanation.
- **A `\boxed{}` that exists syntactically but contains nothing that
  parses to a usable value** (empty, or non-math content) is mapped to
  `no_boxed_answer`, not `extraction_ambiguous` — ambiguity implies
  multiple *disagreeing candidates*, and there are none in that case. A
  judgment call within the closed taxonomy's latitude; flagging the
  reasoning rather than treating it as obvious.
- Changed `tests/test_answer_equivalence.py`'s two stub tests from bare
  `raise NotImplementedError` to `pytest.mark.skipif` with an explicit,
  dated reason pointing at this blocker, so a test run today reads as
  "known-blocked" rather than "broken." `tests/test_taxonomy.py` was
  implemented for real (not skipped) since it has no generation
  dependency at all.

## Negative / unexpected results
- The two math_verify behaviors above (silent set-construction on
  disagreeing boxed values; silent `False` on timeout) are both real,
  reproducible gotchas in a well-maintained, actively-used library — not
  edge cases invented for the sake of defensive coding. Worth remembering
  project-wide: math_verify's defaults optimize for "give me a bool," not
  for "tell me when you couldn't determine one," which is the opposite of
  what invariant #6 needs. Every future call site touching `verify()` or
  `parse()` should be checked against this same assumption before trusting
  a bare return value.
