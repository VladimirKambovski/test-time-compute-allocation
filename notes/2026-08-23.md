## Segmentation conventions: empirical scan before choosing

Per `configs/prms/qwen-math-prm-7b.yaml`'s documented fallback order
(`double_newline` -> `step_prefix` -> `special_token`), scanned 200 real
completions from `notes/scratch/day4_pool.jsonl` before assuming any of
them would apply (`notes/scratch/day5_segmentation.py`):

| Convention | Coverage on 200-completion scan |
|---|---|
| `double_newline` | 200/200 (100%) |
| `step_prefix` ("Step k:" literal) | 0/200 (0%) |
| `special_token` | no recurring exotic delimiter found; no token configured |

This policy's actual non-thinking output style is numbered markdown
(e.g. `1.  **Calculate $r$:**`), not literal `"Step 1:"` -- so
`step_prefix` was expected, going in, to be a non-starter for this
specific policy/pool, and `special_token` has no known applicable token
(none was injected at generation time, and no exotic delimiter recurs
naturally). `double_newline` is the only convention with universal
coverage on this pool. Implemented all three anyway (not just the one
expected to work) -- `step_prefix`/`special_token` return `[]` rather
than silently treating the whole completion as one step when their
pattern doesn't match, per invariant #7's closed-taxonomy discipline
(`step_segmentation_failed`, not a guessed single-step fallback).

## Full-pool PRM scoring: real bug caught and fixed live

Extended the same pipeline to the full N=32 pool (100 problems x 32 =
3200 samples) to make B3 computable at full scale. Script:
`notes/scratch/day5_score_full_pool.py`.

**First launch crashed every task that reached `math_verify.parse()`:**
`ValueError: Math-Verify 'parse' function doesn't support threaded
environment due to usage of signal.alarm()...`. Root cause: answer
extraction/equivalence checking (which calls `math_verify.parse()`
internally, used for correctness labeling) was submitted to the same
`ThreadPoolExecutor` as the PRM network calls -- `signal.alarm()`-based
timeouts only work on the main thread. Fixed by splitting the pipeline:
extraction/equivalence/segmentation (CPU-only) now runs sequentially on
the main thread *before* the executor is created; only the network-bound
PRM `/score` call is parallelized. The 57 tasks that happened to avoid
calling `parse()` at all (already-`length_truncated`-with-no-box
completions, which `extraction.py` short-circuits before parsing) had
already succeeded and written to disk before the crash pattern became
consistent -- resumability picked those up correctly on relaunch, no
data lost, no re-scoring needed for them.

## Reproduce B3: PRM-weighted majority vs plain majority, full scale

Script: `notes/scratch/day5_reproduce_b3.py`. **Real bug caught before
trusting any B3 number**, logged in detail because the fix matters for
every future selector comparison, not just today's: the first version's
`plain_majority` excluded a problem from the denominator entirely on a
tied vote (`selectors/basic.py`'s convention). That gave **0.9733
accuracy on 75/100 problems** -- flatly inconsistent with Day 4's own
frozen G1 baseline for this exact metric on this exact pool (SAMPLE
accuracy = 0.730 on all 100, `notes/2026-08-21.md`). Root cause:
`notes/scratch/day4_analysis.py::deterministic_action_values` (the
actual G1 gate computation) counts a tied-or-empty vote as **incorrect**,
always in a denominator of 100 -- it does not exclude it. Excluding ties
instead disproportionately drops the hard, low-consensus problems (which
correlate with the majority vote being wrong), which is exactly why it
inflated accuracy so sharply. **Fixed to match `day4_analysis.py`'s
convention**, since that's the one already reported as the project's
headline SAMPLE-accuracy number; verified the fix by cross-checking the
recomputed plain-majority accuracy against 0.730 exactly (see script
output below) before trusting the PRM-weighted number built on top of
it.

**This surfaces a real, unresolved inconsistency**: `selectors/basic.py`
(the Day-8-designated MUST selector, already built ahead of schedule)
uses the exclude-on-tie convention, which disagrees with the convention
the project's actual gate computations have been using. Not patched in
`selectors/basic.py` today -- that's a Day 8 design decision (it directly
feeds the oracle action labels), flagged here rather than fixed
unilaterally, since which convention Day 8 should use has downstream
consequences beyond today's script.

**Full-scale B3 result (100 problems, N=32):**

```
selector                     n   n_correct    accuracy
plain_majority              100         73      0.7300
prm_weighted_majority       100         73      0.7300
prm_best_of_n               100         72      0.7200

PRM-weighted majority vs plain majority margin: +0.00pp (published ~1.4pp)
PRM best-of-N vs plain majority margin:          -1.00pp
```

Checked whether the tied *accuracy* (73 vs 73) hides offsetting flips
(some problems gained, others lost, net zero) -- it does not: **zero
problems differ in correctness between plain majority and PRM-weighted
majority.** PRM-weighting the vote never changes the winning answer on
any of the 100 problems in this pool. PRM best-of-N is one problem worse
than plain majority (72 vs 73) -- a real, if small, downgrade from
skipping voting entirely in favor of the single top-scored sample.

**B3 verdict:** the literal accept condition ("PRM >= maj at small N")
technically **passes** (0.730 >= 0.730, a tie counts), but the
"margin consistent with published ~1.4%" clause **does not** -- the
actual margin is 0.00pp, not ~1.4pp, and mechanistically that's because
PRM-weighting never flips a single decision on this pool. This is not a
new, separate finding -- it is the same fact Day 4's G1 investigation
already surfaced (SELECT-only oracle win rate 1% on this exact pool)
showing up again from a different angle: a real PRM, not just the
oracle-proxy ceiling, also finds essentially nothing to do differently
from plain majority here. Reported as a second, independent confirmation
of the existing narrow-action-space decision, not reopening it.

## Resolved: the tie-handling discrepancy

Fix was narrower than it might have looked from the TODO: `plain_majority`
itself doesn't need to change -- returning `is_correct=None` on a tie is
an honest per-problem signal, not the bug. The actual inconsistency was
in how a LIST of those results gets turned into one accuracy number.
Added `selectors/basic.py::accuracy()` as the single canonical
aggregator: `is_correct in (None, False)` both count toward the
denominator and neither toward the numerator, matching
`day4_analysis.py::deterministic_action_values` exactly. Every selector
(`plain_majority`, `prm_weighted_majority`, `prm_argmax`) returns the
same `MajorityResult` shape specifically so all of them get scored
through this one function -- a per-selector inconsistency here would
silently reopen the exact bug this closes.

Updated `selectors/basic.py`'s docstring (TODO -> RESOLVED, with the
reasoning) and checked off the corresponding `docs/roadmap.md` Day-8
bullet, rather than leaving either as a dangling reference to a decision
that's actually been made.

regardless of caller thread. `extraction.py`/`equivalence.py` now import
`parse`/`verify` from this wrapper instead of `math_verify` directly --
zero other code changes needed at either call site.

`ThreadPoolExecutor` worker thread (not just "the parity test happens to

timeout (doesn't silently disable protection to fix the crash).
